01

설계 원칙과 대회 요건

핵심 통찰

평가지표 8개 중 5개가 "틀리지 않기"에 해당합니다 — 정확성, 근거 완전성, 근거 기반, 안전성, 정보한계 대응. "잘 답하기"는 요구사항 충족·추론 논리성 2개뿐입니다. 이 대회는 잘 답하는 시스템이 아니라 틀리지 않는 시스템을 뽑습니다.

대회 제약

절대 조건

LLM은 HyperCLOVA X만 사용 가능 — 위반 시 평가대상 제외. NLI·임베딩 모델이 이 범위에 포함되는지는 미확인이며 디스코드 확인이 필요합니다. 확인 전까지 모든 검증 계층을 LLM 없이 결정론적 코드로 구현했습니다.

09.06 마감 후 커밋·배포 시 실격 — 핫픽스 기회가 없습니다.

평가 방식

세션 없는 단일 GET 요청 /answer?question_id=&question= → JSON 5필드(question_id, question, retrieved_context, think_trace, answer). 다회차 대화가 불가능하므로 역질문과 조건부 답변을 한 응답에 함께 담아야 합니다.

03

사전 검색 계층 (L0)

질의 분석을 문서에 접지시키는 저비용 개략 검색. LLM 호출 없이 동작하므로 이 계층을 추가해도 호출 횟수는 늘지 않습니다.

왜 필요한가 — 기존 순서의 실제 약점

L1이 무엇을 근거로 판단하는가

기존 순서는 질의 분석 → 검색이었습니다. 그러면 L1이 요구사항 슬롯과 호출할 계산함수를 정할 때, 판단 근거는 모델의 내부 지식이 됩니다.

그런데 이 도메인에서 모델 내부 지식은 신뢰할 수 없습니다. 세법이 개정됐고(700만원→900만원, 1,200만원→1,500만원), 모델이 구법을 알고 있으면 슬롯 자체가 틀리게 추출됩니다. 검색은 그 뒤에 오므로 이미 늦습니다.

설계 — 2단 검색

구어체 질의("명퇴하는 교사예요…")를 날것으로 검색하면 품질이 나쁩니다. 질의 분석이 앞에 있는 이유가 그것입니다. 따라서 순서를 뒤집는 것이 아니라 단계를 나눕니다.

L0 · 개략 검색 목적: 방향 잡기 비용: LLM 0회 → 어떤 영역인가 · 문서가 쓰는 용어는 무엇인가 · 구법 문서가 있는가 L1 · 질의 분석 L0 접지 정보를 받아 슬롯·도구·계획 산출 L3 · 정밀 검색 구조화된 스펙으로 실제 근거 확보 L4 · 필터 구법탐지 · 엔티티충돌 · 가입자격 · 하드제약
절대 원칙 — L0 결과는 답변 근거가 아니다

L0는 Exploitation 필터를 거치지 않았습니다. 따라서 L0가 찾은 문서를 답변 인용에 쓰면 "사용한 것만 인용" 원칙이 무너지고 검증되지 않은 근거가 답변에 섞입니다.

L0 산출물 용도 — 질의 분석 접지, 도메인 커버리지 판정, 조기 거절
L0 산출물 금지 — 답변 인용, retrieved_context 기재, 계산 파라미터 공급

그래서 L1에 넘기는 것도 원문 전체가 아니라 영역과 용어 목록뿐입니다. 원문을 통째로 주면 L1이 이를 근거로 착각해 답변을 만들어낼 위험이 있습니다.

동작 검증

질의 "연금저축 세액공제 얼마까지 되나요?" 검색 범위에 구법 문서(700만원 기준)가 포함된 상황 L0 접지 — 영역 ['제도', '세제'] · 후보 1건 · 커버리지 0.55 · 구법 의심 1건 ── L1에 주입되는 접지 정보 ── 관련 영역: 제도, 세제 문서에서 사용하는 용어: 세액공제, 연금저축 주의: 검색 범위에 법 개정 이전 수치를 담은 문서가 있습니다 (OLD_01). 현행 기준으로 판단하십시오. ※ 위 정보는 분석 참고용이며 답변 근거가 아닙니다. 근거는 이후 검색 단계에서 확보합니다.
이 사례의 의미

L0가 구법 문서를 L1이 분석하기 전에 경고합니다. 기존 순서였다면 L1이 700만원 기준으로 슬롯을 뽑은 뒤에야 발견됐을 문제입니다. 오류를 뒤에서 잡는 것보다 앞에서 막는 쪽이 항상 싸고 안전합니다.

조기 거절 — LLM 호출 전에 판정

도메인 밖 질의에 LLM 호출을 소모할 이유가 없습니다. L0에서 판정하면 LLM 호출 0회로 거절이 완결됩니다.

질의 "비트코인 지금 사도 될까요?" L0 조기 거절 — 도메인 밖 신호 '코인' 감지 응답 (5필드 전부 채움) retrieved_context : "근거 문서 없음 — 제공 자료 범위에서 관련 문서를 찾지 못했습니다." think_trace : "L0 사전 검색 단계에서 도메인 범위 밖으로 판정. 이후 단계를 수행하지 않고 종료." answer : 범위 밖임을 알리고 연금 관련 질문을 안내

비용 절감이자, 최고 가중치 지표인 "정보한계 대응"에 대한 가장 확실한 대응입니다. retrieved_context를 비우지 않는 점도 중요합니다 — 스키마 위반이 되고 "모든 답변에 근거 문서 표시" 요건에도 어긋나기 때문입니다.

장애 내성

검색 함수 예외 발생 → "L0 개략 검색 실패(DB down) — 접지 없이 분석 진행" domain_covered: True · early_refuse: False

L0가 죽어도 파이프라인은 중단되지 않습니다. 접지 정보 없이 L1이 진행하며, 실패 사실은 think_trace에 기록됩니다. 보조 계층이 주 경로를 막아서는 안 됩니다.

계획 감사 — L1 산출물을 실행 전에 심사

L0와 함께 추가된 두 번째 보완입니다. 기존에는 L1이 산출한 실행 계획을 아무도 검사하지 않고 곧바로 실행했습니다. L1이 잘못된 함수를 고르면 이후 전 단계가 그 위에서 진행되고, L6 감독은 이미 만들어진 답변만 봅니다 — 원인이 아니라 증상을 보는 셈이었습니다.

계획 감사 항목 (LLM 호출 없음) · planned_calls가 CALC_REGISTRY 화이트리스트에 있는가 · 인자 구조가 유효한가 · 계산 슬롯이 있는데 호출 계획이 비었는가 · L0가 도메인 미커버로 판정했는데 계산을 계획했는가 · 계획 단계가 과도한가 (시간 예산 초과 위험) 검증 ③ 미등록 함수 '존재하지_않는_함수' 호출 계획 → REVISE · 교정된 호출: ['사적연금_납입한도_세액공제_계산'] 검증 ④ 커버리지 없는데 계산 계획 → DOWNGRADE · 답변 등급 강등 → PARTIAL

③에서 감사가 미등록 호출만 제거한 안전한 계획을 반환합니다. 판정만 하는 것이 아니라 실행 가능한 형태로 교정합니다.

채택 판단 근거

두 보완 모두 LLM 호출을 늘리지 않습니다. L0는 BM25/키워드 스캔, 계획 감사는 화이트리스트 대조입니다. 따라서 레이턴시·비용 리스크 없이 ① 분석 접지 ② 조기 거절 ③ 계획 검증 세 가지를 얻습니다.

반대로 채택하지 않은 것: L0 결과를 답변 근거로 쓰는 것, L0에 LLM을 붙여 질의를 재작성하는 것. 전자는 검증 우회이고 후자는 호출 증가 대비 이득이 불확실합니다.

04

계층별 명세

L0(사전 검색)와 계획 감사는 §03에서 이미 상세히 다뤘으므로 여기서는 L1부터 L6까지를 다룹니다.

L1 · 질의 분석 (Function calling)

단일 호출에서 세 가지를 동시에 산출합니다 — ① 요구사항 슬롯 ② 호출할 계산함수와 인자 ③ 실행 계획. ②가 에이전트성의 근거이고, ③이 think_trace의 원본이 됩니다. 이 산출물은 §03의 계획 감사를 거친 뒤에만 실행됩니다.

출력 스키마 (개요) { "asked_for": [{"id":..., "type":"fact|calculation|comparison", "required":true}], "user_conditions": {"account_type":..., "age":..., "amount":...}, "planned_calls": [{"function":"연금수령한도_계산", "args":{...}}], "plan": ["자격 확인 → 한도 계산 → 조건별 비교"] } 안전장치 — planned_calls는 CALC_REGISTRY 화이트리스트 검증을 거친다. 미등록 함수명이면 거부하고 매핑 테이블로 결정론적 폴백.

L2 · 함정 감지

26종 규칙으로 질의를 스캔해 잘못된 전제·혼동 위험을 식별합니다. critical 규칙이 걸리면 답변가능성 판정을 한 단계 보수화합니다 (ANSWER→PARTIAL, PARTIAL→ASK_BACK). 상세는 §07.

Exploration → Exploitation (순차)

병렬이 아니라 순차입니다. 탐색이 후보를 넓히고 필터가 자격 없는 것을 걷어냅니다. 순서가 뒤집히면 "총보수 최저인데 가입 불가능한 상품"을 추천하게 됩니다(§07 D1).

Exploitation 필터 순서 1. 구법 수치 탐지 — 법 개정 이전 문서를 세제 근거에서 제외 2. 엔티티 충돌 제거 — 질의 대상과 다른 상품·조항 배제 (비교 질의는 예외) 3. 가입자격 판정 — 계좌유형 × 판매클래스 적합성 4. 하드 제약 검증 — 세제 한도·약관 위반

세법 검증에서 정정한 3건

① 과세 대상 범위 — '초과분'이 아니라 '전액'

제공문서 원문의 과세 객체는 '초과분'이 아니라 '연금소득'입니다. 1,500만원은 공제액이 아니라 과세 방식이 갈리는 기준선입니다.

연 2,000만원 수령 시 — 초과분 과세 82.5만원 vs 전액 과세 330만원 (4배 차이)

② 세율 기준 불일치 — 7,680만원의 정체

규격서 임계값 7,680은 576 ÷ (0.24 − 0.165)로 도출 자체는 정확합니다. 문제는 좌변이 국세 기준 누진세액인데 우변이 지방소득세 포함 세율이라는 것입니다.

기준을 통일하면 576 ÷ (0.24 − 0.15) = 6,400만원. 6,400~7,680 구간에서 유불리 판정이 뒤집힙니다.

③ 과세표준 ≠ 총연금액

누진세율은 총연금액이 아니라 연금소득공제·종합소득공제를 뺀 과세표준에 적용됩니다. 다만 이 공제 수치는 제공문서에 없어 일반 세법 기준이며, 개인 사정 미확인 시 ASK_BACK 대상입니다.

09

감독 계층 — 법무팀과 사외이사

기존 검증 계층은 기계적 대조였습니다. 이 계층은 판단하고 시정을 지시합니다. 검사와 감독은 다른 일입니다.

검증과 감독의 차이

검증(verification) — 이 숫자가 근거에 있는가. 참/거짓 판정. 기계적.

감독(supervision) — 이 답변을 내보내도 되는가. 판단, 그리고 무엇을 어떻게 고칠지 지시.

기업으로 치면 전자는 회계 대사이고, 후자는 법무팀과 사외이사의 역할입니다. 감독은 통과·불통과만 정하지 않고 시정 지시를 내리며, 필요하면 스스로 등급을 강등시킵니다.

구성 — 2원 감사 체계

감독은 결정론적 감사와 HyperCLOVA X 의미 감사가 함께 수행합니다. 서로 잡을 수 있는 영역이 다르기 때문입니다.

LLM에게 감독을 맡기는 것은 위험을 동반합니다. 판정을 뒤집을 수 있으면 기존 방어선이 무력화되기 때문입니다. 그래서 LLM 감사는 심각도를 올릴 수만 있고 내릴 수 없도록 설계했습니다.

결정론적 BLOCK → LLM이 무엇이라 해도 BLOCK 확정 (LLM 호출 생략) 결정론적 REVISE → LLM이 BLOCK 주장 시 BLOCK, APPROVE 주장해도 REVISE 유지 결정론적 APPROVE → LLM이 문제 발견 시 상향, 아니면 APPROVE

이 단조성(monotonicity) 덕분에 LLM 감사를 추가해도 시스템이 기존보다 관대해지는 일이 구조적으로 발생하지 않습니다. 검증 결과: 결정론=REVISE + LLM=APPROVE → 최종 REVISE 유지 확인.

감사 독립성 — 감사자는 생성 과정을 보지 않는다

의미 감사에 전달되는 것은 질문 · 최종 답변 · 근거 문서 · 계산 결과뿐입니다. 생성 시의 프롬프트와 추론 과정은 의도적으로 제외합니다.

생성 논리를 함께 보면 그 논리에 동조하게 되므로, 독자의 입장에서 결과물만 보고 판단하게 만드는 것입니다. 감사인이 경영진의 의사결정 논리가 아니라 재무제표를 보는 것과 같은 원리입니다.

동작 검증 — 의미 감사가 잡아낸 것

답변 "연금 개시 11년차이시면 퇴직소득세 감면율은 40%가 적용됩니다." 계산 {"reduction_rate": 0.4, "source": "doc40"} 근거 "연금실제수령연차 11~20년차는 이연퇴직소득세의 60%를 적용한다." 결정론적 감사 → 전부 통과 · 수치 대조: 0.4는 계산 결과에 실재 ✓ · 준법: 단정 표현 없음 ✓ · 이상치: 범위 정상 ✓ · 적합성: 조건 불일치 없음 ✓ HyperCLOVA X 의미 감사 → REVISE [의미 정합성] 연금수령연차와 연금실제수령연차를 구분하지 않고 감면율을 단정 지시: 실제 인출 이력에 따라 감면 기준 연차가 달라짐을 명시할 것 확인 요청: ['연금 개시 이후 실제 인출한 연도 수']
이 사례가 증명하는 것

숫자는 근거에 실재하고, 규칙 위반도 없습니다. 결정론적 계층은 전부 통과시킵니다. 그런데 설명이 틀렸습니다 — 개시 11년차라도 실제 인출 이력이 없으면 감면 기준 연차가 쌓이지 않기 때문입니다(doc40이 직접 경고하는 함정 B1).

이것이 앞서 "수치 검증기가 막지 못한다"고 명시했던 의미 오류이며, HyperCLOVA X 참여로 이 공백이 메워졌습니다.

실패 처리 — 감사 미수행을 숨기지 않는다

검증 중 실제 버그를 발견해 수정했습니다. LLM 호출이 실패했는데 기록이 "지적사항 없음"으로 표시되고 있었습니다. 감사가 수행되지 않은 것과 문제가 없는 것은 다릅니다.

호출 실패 → "감독 심사 APPROVE — 지적 1건 [의미감사/CALL_FAIL] 의미 감사 호출 실패: timeout 결정론적 판정만 적용" 파싱 실패 → "[의미감사/PARSE_FAIL] 감사 응답을 해석하지 못함 의미 감사가 수행되지 않음" 결정론 BLOCK → "[의미감사/SKIPPED] 이미 차단 — 의미 감사 생략"

세 경우 모두 think_trace에 명시적으로 기록되어, 채점자가 어떤 감사가 실제로 수행됐는지 확인할 수 있습니다.

판정 체계

APPROVE 승인 REVISE 시정 후 재생성 — 지시문을 Supervisor에 재주입 (1회 제한) DOWNGRADE 답변 등급 강등 — ANSWER → PARTIAL → ASK_BACK BLOCK 차단 — fallback 템플릿으로 대체 여러 지적이 동시 발생 시 가장 무거운 판정을 채택한다.

결정론적 감사 검증 — 7개 시나리오

① "가장 유리합니다. 추천드립니다" → REVISE [준법/ASSERTIVE] 단정적 표현 ② "연금수령한도는 12,000,000만원입니다" → BLOCK [이상치/UNIT_SUSPECT] 원/만원 단위 혼동 의심 ③ "세액은 -50만원입니다" → BLOCK [이상치/NEGATIVE] 금액이 음수 ④ 역질문 5건 나열 (부분 답변 가능) → REVISE [부담/TOO_MANY_QUESTIONS] + [부담/AVOIDABLE_ASKBACK] 역질문 축소 → ['계좌유형', '연령'] ← 스스로 추려냄 ⑤ "C-RJ가 총보수 0.154%로 가장 저렴합니다" (연금저축 이용자) → REVISE [적합성/INELIGIBLE_PRODUCT] 가입 자격 없는 상품 ⑥ "11년차이시면 40% 감면됩니다" (B1 함정 감지됨) → REVISE [적합성/TRAP_UNADDRESSED] 교정 취지 없음 ⑦ 조건부 서술 + 근거 인용 + 확인 항목 1건 → APPROVE

④가 결정론적 감사의 성격을 잘 보여줍니다 — 역질문 5건을 감지하고 스스로 2건으로 추려냈습니다. 검사가 아니라 결정입니다.

비용

의미 감사는 LLM 호출 1회를 추가합니다. 다만 결정론적 감사가 이미 BLOCK이면 호출을 생략하므로, 명백한 오류 케이스에서는 비용이 발생하지 않습니다.

최선 L1 분석 + L5' 생성 = 2회 보통 L1 + L5' + L6 의미감사 = 3회 최악 L1 + L5' + L6 + L5' 재생성 = 4회 (재생성 1회 제한) 차단 L1 + L5' (의미감사 생략) = 2회

재생성 1회 제한은 무한 루프와 레이턴시 폭증을 막기 위함입니다. 재생성 후에도 통과하지 못하면 fallback 템플릿으로 축퇴합니다.

남는 한계 — 정직하게 기록

동일 모델이 자신의 출력을 감사하므로 blind spot이 상관될 수 있습니다. 생성 시 놓친 것을 감사 시에도 놓칠 가능성이 구조적으로 존재합니다.

따라서 의미 감사는 결정론적 감사를 대체하지 않고 보완합니다. 결정론적 계층이 여전히 1차 방어선이며, 권한 계층이 이를 제도적으로 보장합니다. 감사 독립성(생성 과정 미제공)은 이 상관성을 낮추는 완화책이지 해소책은 아닙니다.

감독 기록은 think_trace로

감사 결과는 think_trace에 그대로 기록됩니다. 채점자가 "이 시스템이 무엇을 점검했는지"를 직접 확인할 수 있으며, 정성평가의 기술완성도·리스크 관리 항목에 작용합니다. 지적사항이 없을 때도 승인 기록을 남겨 감독이 실제로 수행됐음을 보입니다.

에이전트성 확보

문제 — 세 Agent는 자율 판단을 하지 않는다

Exploration/Exploitation/Prediction은 각각 벡터검색·SQL필터·함수호출이며, 학술적 의미의 Agent(자율적 도구 선택·의사결정)가 아닙니다. "이게 왜 에이전트인가"라는 질문에 방어가 필요합니다.

기각된 방안 — fallback 시 LLM 대응

① 트리거가 LLM 판단이 아니라 시스템 예외입니다. LLM은 복구 전략을 선택하지 않고 정해진 경로에서 문장만 생성합니다.
② 정상 경로에서는 자율성이 0이므로 "고장났을 때만 에이전트"가 됩니다.
③ fallback은 가장 테스트가 덜 된 경로입니다. 거기에 자율성을 두면 "검증이 가장 부족한 부분이 가장 자유롭게 동작"하게 되어 안전성 지표와 충돌합니다.

채택 — 추가 LLM 호출 0회로 해결

방안 1 · Function calling을 '도구 선택'으로 격상
LLM이 CALC_REGISTRY 15종 중 호출할 함수와 인자를 직접 선택. 이것이 tool-use agency의 표준 정의이며, 같은 호출의 스키마 확장만으로 달성됩니다.

방안 2 · 실행 계획 명시 산출
같은 호출에서 실행 계획을 구조화 출력. 계획서가 그대로 think_trace가 되어 응답 스키마 필수 필드를 동시에 채우고 "추론 논리성" 지표에 대응합니다.

방안 3 · 감독 계층 (§09)
가장 결정적인 근거입니다. 감독 계층은 검사만 하지 않고 시정을 지시하고, 답변 등급을 강등시키고, 역질문을 스스로 추려냅니다. 행동을 선택하고 그 선택이 후속 실행(재생성 여부, 등급, 질문 개수)을 바꾸므로 에이전트의 정의를 온전히 충족합니다.

결과: "LLM이 도구를 선택하고 계획을 세우며, 감독 계층이 결과를 심사하고 시정을 지시한다." 방어가 아니라 설계 의도의 설명이 됩니다.

감독 계층이 채운 구조적 공백

기존 설계에는 "이 답변을 내보내도 되는가"를 판단하는 주체가 없었습니다. 수치 대조는 숫자만 봤고, 요구사항 검증은 누락만 봤습니다. 규칙 위반, 계산 이상치, 사용자 부적합, 과도한 역질문은 어느 계층도 보지 않았습니다.

기업이 스스로 감사하지 않으면 법무팀과 사외이사가 그 역할을 하듯, 생성 계층과 분리된 독립 감독 기구가 필요합니다. 생성하는 주체가 스스로를 심사하면 그것은 감독이 아닙니다.

발표 논리

자율적인 것: 도구 선택, 실행 계획, 답변 생성 (Supervisor 단일 호출)
결정론적인 것: 제약 검증, 수치 계산, 근거 필터, 답변가능성, 수치 대조, 인용, fallback

이 구분 자체가 논리입니다 — "판단이 필요한 곳에는 자율성을, 정확성이 필요한 곳에는 결정론을 배치했다." 특히 Exploitation을 일부러 결정론적으로 둔 것은 약점이 아니라 설계 성숙도의 증거입니다. 금융 도메인에서 하드 제약에 자율성을 주는 것은 위험합니다.

폐기 — "유한 속 무한" 슬로건

실제 구현이 depth cap을 건 유한 파이프라인이라 구현과 괴리됩니다. 대체 메시지는 "자율적 도구 선택 + 결정론적 검증".

사법 리스크 — 일반적 고려사항

자본시장법 특정 상품 투자판단 자문을 영업으로 제공 시 투자자문업 등록 대상. → 조건부 제시 구조가 리스크를 낮춥니다.

금융소비자보호법 불확실한 사항에 대한 단정적 판단 제공 금지. → 안내서의 "단정적 추천 지양"이 이 조항의 반영으로 보입니다. 미래 변수를 '가정'으로만 다루는 설계가 정확히 부합합니다.

세무사법 세무 상담의 업 영위는 자격 영역. 일반적 세제 정보 제공은 통상 해당하지 않음. → 개인별 세액 확정 제시와 계산 구조 설명을 구분하고, ASK_BACK으로 경계를 지킵니다.

개인정보보호법 질의에 나이·소득·가족관계 포함 가능. 로그 최소화·미저장 원칙 명시.

이는 일반적 고려사항이며 법률 자문이 아닙니다. 기술제안서에 면책·정보제공목적 문구를 반드시 삽입하십시오.
